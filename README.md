# Litra Glow CLI

A standalone Rust CLI for Apple Silicon macOS. It talks directly to the Logitech Litra Glow
over USB HID. No Node runtime, Logitech software, or background service is needed.
The existing Node scripts remain here for reference.

## Install

Once the first release is published:

```sh
brew install dreamorosi/tap/litra
```

Homebrew downloads a prebuilt binary from GitHub Releases. It does not compile
Rust or require Logitech software. Releases support Apple Silicon only.

### From source

Install Rust using [rustup](https://rustup.rs). Building also requires Apple's
command line tools, available with `xcode-select --install`.

From this directory:

```sh
cargo install --path . --locked
```

This installs `litra` in `~/.cargo/bin`. That directory must be on your `PATH`.

Alternatively, build a binary to copy to another Mac:

```sh
cargo build --release --locked
install -m 755 target/release/litra /usr/local/bin/litra
```

The destination directory must exist and be writable. The receiving Apple
Silicon Mac does not need Rust installed.

## Use

```sh
litra                 # Toggle using the actual device state
litra on
litra off
litra toggle
litra status          # Read actual state, print on/off, update saved state
litra status --cached # Read saved state without accessing USB
litra --help
```

Commands print the resulting state. Errors go to stderr and exit with code 1.
Only the Litra Glow is supported. If multiple lights are connected, the CLI
refuses to guess which one to use.

## State

The CLI queries the light for its power state. It never decides how to toggle
from a saved file, so physical-button changes and unplugging don't make the
next toggle use stale state.

After a successful status query or confirmed power change, the CLI writes
`~/.config/litra/state.txt`, compatible with the existing Node script. If
`XDG_CONFIG_HOME` is set, it uses `$XDG_CONFIG_HOME/litra/state.txt` instead.
It creates the directory automatically and replaces the state file atomically.
The `state.txt` in this project directory is not used.

`status --cached` labels its output as last-known. A saved state does not prove
that the light is connected or still in that state. USB failures leave the saved
state unchanged. A command can change the light successfully and still fail
while verifying or saving the result; the error explains this when saving fails.

Concurrent CLI calls use a file lock. A second invocation fails with a message
to try again rather than racing the first. Other software and the physical
button do not honor this lock.

## Development

```sh
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
```

Tests use a fake light and do not change the attached hardware. Actual USB
communication needs testing with a connected Litra Glow. State queries have a
one-second read timeout.

## Releases

Builds run entirely on GitHub-hosted runners. No locally compiled artifact is
uploaded. The process follows `create-cdk-app-cli` using cargo-dist, manual
version/tag preparation, and a separately dispatched release.

- `dist-workspace.toml` configures cargo-dist 0.33.0, the Apple Silicon target,
  and `dreamorosi/homebrew-tap`.
- `.github/workflows/release.yml` is generated by `dist generate`. It builds the
  archive and checksums, generates `litra.rb`, creates the GitHub Release, and
  commits only that formula to the tap.
- `.github/workflows/ci.yml` runs formatting, Clippy, tests, and CLI smoke tests
  on Apple Silicon. `.github/build-setup.yml` inserts checks and tests into the
  release build itself, so a failed test blocks publishing.
- Pull requests build downloadable release artifacts but do not publish a
  release or update the tap.
- `rust-toolchain.toml` pins Rust. `Cargo.lock` pins Rust dependencies. Action
  references are pinned to commit SHAs.

### One-time GitHub setup

1. Create the public repository `dreamorosi/litra-cli` with default branch
   `main`, then push the project after approval. Public release downloads are
   needed for this Homebrew setup.
2. Enable GitHub Actions. The version/tag workflow needs permission to write
   repository contents. Branch rules must allow its bot to update `main`, or
   prepare version changes through a reviewed PR and create the tag separately.
3. Add a repository Actions secret named `HOMEBREW_TAP_TOKEN`. Use a fine-grained
   PAT with access to `dreamorosi/homebrew-tap` and Contents read/write permission.
   The default `GITHUB_TOKEN` handles releases in `litra-cli`, but cannot write to
   the separate tap repository. GitHub cannot reveal or copy the existing CDK
   repository's secret value; set the token here separately. Do not put it in a
   file or chat.

### Publish a version

Both workflows below modify remote repositories. Obtain approval before
dispatching either one. No PR merge automatically publishes a release.

1. Wait for CI on `main` to pass.
2. Run **Bump version and tag** on `main`. Choose `none` for the first `v0.1.0`
   release, or `patch`, `minor`, or `major` for later releases. It tests the
   project, commits version changes when needed, and pushes the tag. It does not
   publish anything to Homebrew.
3. Run **Release**, selecting the newly created tag as the workflow ref and
   supplying that exact tag as the `tag` input. For the first release, both must
   be `v0.1.0`. The release checks reject a branch ref or a mismatched tag.
4. The workflow builds `litra-aarch64-apple-darwin.tar.xz`, calculates checksums,
   publishes it at `dreamorosi/litra-cli`, and pushes `Formula/litra.rb` to
   `dreamorosi/homebrew-tap`. This is a direct tap commit, not a tap PR.
5. Verify installation on an Apple Silicon Mac:

   ```sh
   brew update
   brew install dreamorosi/tap/litra
   litra --version
   litra status
   ```

Use `brew upgrade dreamorosi/tap/litra` for later releases.

To test packaging without publishing, dispatch **Release** on `main` with
`tag` set to `dry-run`. It uploads workflow artifacts only. Prerelease versions
are not published to the tap.

### Maintain release configuration

Use the configured cargo-dist version when regenerating files:

```sh
dist generate
dist generate --check
dist plan
```

Do not hand-edit `release.yml`. Update action pins in `dist-workspace.toml`,
sync matching checkout pins in the handwritten workflows, then regenerate.
Dependabot ignores the action references managed by cargo-dist to avoid making
the generated workflow drift. It still proposes Rust dependency updates.
